# bypass

**bypass** — локальный control plane для развёртывания VPN-стека на чистом Ubuntu VPS через Ansible. Проект объединяет несколько протоколов: Hysteria 2, VLESS Reality TCP и OpenFlux, а также умеет управлять клиентами, генерировать подписки и деплоить сервисы на удалённый сервер.

Основная идея простая: вся логика управления остаётся на вашей машине, а на VPS запускаются только нужные сервисы и небольшой subscription-server.

## Что умеет проект

- валидировать TLS-сертификаты;
- поднимать DNS A-запись через Cloudflare;
- хранить секреты по VPS-адресу;
- создавать и управлять клиентами;
- генерировать subscription URLs;
- генерировать полный Xray JSON с маршрутизацией российских сервисов напрямую;
- запускать деплой через Ansible;
- отслеживать прогресс деплоя в realtime через SSE;
- поддерживать OpenFlux как один из протоколов туннеля.

## Архитектура

- backend: FastAPI, Python
- frontend: статический UI, отдаётся через FastAPI
- orchestration: Ansible для VPS
- storage: JSON-файлы в `data/secrets/`
- target server: Ubuntu VPS, где запускаются xray/hysteria/openflux/subscription сервисы

Ключевой модуль: `vpnforge/main.py`.
Ключевая логика OpenFlux: `vpnforge/openflux_manager.py`.
Ansible-плейбук деплоя: `ansible/deploy.yml`.

## Требования

Перед запуском убедитесь, что установлено:

- Python 3.11+
- [Poetry](https://python-poetry.org/)
- Ansible (`ansible-playbook` должен быть в `PATH`)
- SSH-доступ к целевому VPS (ключ или пароль)
- Для DNS/Cloudflare: Cloudflare API token (опционально)

Для установки Ansible можно использовать, например:

```bash
pipx install ansible-core
```

## Установка зависимостей

```bash
cd <путь_к_проекту>
poetry install
```

Если проект использует переменные окружения, создайте `.env` или задайте нужные значения в shell. В проекте есть параметры, которые читаются через `pydantic-settings`, а также поддерживаются переменные с префиксом `VPNFORGE_`.

Типичные переменные:

- `VPNFORGE_DATA_DIR` — каталог для секретов и run-данных
- `VPNFORGE_LOG_LEVEL` — уровень логирования
- `VPNFORGE_ANSIBLE_BIN` — путь к `ansible-playbook`
- `VPNFORGE_ANSIBLE_TIMEOUT` — таймаут деплоя
- `VPNFORGE_CF_API_TOKEN` — токен Cloudflare для DNS

## Запуск проекта

### Запуск backend

```bash
cd <путь_к_проекту>
poetry run uvicorn vpnforge.main:app --host 127.0.0.1 --port 8000
```

После этого приложение будет доступно по адресу:

- UI: http://127.0.0.1:8000/
- health check: http://127.0.0.1:8000/api/health

При первом запуске создайте локальный профиль. Имя должно быть длиной от 2
до 40 символов, пароль от 8 до 128 символов. Чтобы сохранить доступ к демо,
которое запускали в старой версии, используйте прежнее имя профиля и тот же
адрес в браузере. При следующих посещениях вход выполняется по имени и паролю.

Хеш пароля с индивидуальной солью и хеши сессий хранятся в
`data/auth/auth.sqlite3` (путь зависит от `VPNFORGE_DATA_DIR`). Панель и
управляющие API проверяют сессию. Проверка состояния и подписки по клиентскому
токену доступны отдельно. Панель предназначена для локального запуска.

### Проверка

```bash
curl http://127.0.0.1:8000/api/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

### Локальный демодеплой через Molecule

Для демо установите дополнительные зависимости в окружение проекта:

```bash
poetry run python -m pip install 'molecule==26.4.0' 'ansible-core>=2.19,<2.21'
```

Запустите backend командой выше. Откройте панель, выберите «Демо» и
нажмите «Тестовые данные», затем «Запустить демо». Дождитесь
надписи «Симуляция завершена». Обновите страницу и проверьте, что остались
адрес, протокол и строка «Последнее демо». При повторном входе используйте
то же имя профиля и открывайте панель по тому же адресу.

Для проверки напрямую через API отправьте те же поля формы, что и для
обычного деплоя, на `POST /api/deploy/demo`. SSH, Cloudflare и сертификаты
можно заполнить тестовыми значениями. Для адреса достаточно непустой
строки, а в настройках нужно включить хотя бы один протокол.

После создания профиля можно войти через `curl`. Подставьте своё имя вместо
`demo`. Пароль вводится скрыто и передаётся через стандартный ввод.

```bash
bypass_cookies="$(mktemp)"
printf 'Пароль bypass: '
IFS= read -r -s bypass_password
printf '\n'
printf '%s' "$bypass_password" | curl --fail-with-body -sS -c "$bypass_cookies" \
  --data-urlencode 'profile=demo' --data-urlencode 'password@-' http://127.0.0.1:8000/login
unset bypass_password

curl --fail-with-body -sS -b "$bypass_cookies" http://127.0.0.1:8000/api/deploy/demo \
  --form-string 'payload={"ip":"203.0.113.10","ssh_user":"demo","ssh_password":"mock","domain":"vpn.example.test","protocols":{"hysteria2":true}}'
```

Возьмите `job_id` из ответа и откройте поток логов:

```bash
curl -N -b "$bypass_cookies" 'http://127.0.0.1:8000/api/deploy/stream/<job_id>'
curl -sS -b "$bypass_cookies" -X POST http://127.0.0.1:8000/logout
rm -f "$bypass_cookies"
```

Molecule локально создаёт JSON-описание тестового деплоя, проверяет, что
повторный прогон не меняет файл, и сверяет его с параметрами запроса. В
сценарий передаются только адрес, домен, тип окружения и выбранные протоколы.
Для прогона достаточно localhost. Временные файлы удаляются по завершении.

### Что показать в минутном видео для ИДЗ1

1. До 10 секунд. Откройте папку bypass, покажите Codex и выбранную модель, затем команду запуска.
2. До 20 секунд. Покажите заголовки `PRD.md` и `DESIGN.md`, затем референс Railway.
3. До 50 секунд. Откройте браузер, войдите в заранее созданный локальный профиль, подставьте тестовые данные и запустите демо. Покажите журнал и итоговый статус.
4. До 60 секунд. Обновите страницу и покажите строку «Последнее демо» и восстановленный адрес.

### Сертификат уже находится на VPS

В секции **DNS & CERTS** выберите **уже на VPS** и укажите абсолютные пути,
например `/etc/letsencrypt/live/vpn.example.com/fullchain.pem` и
`/etc/letsencrypt/live/vpn.example.com/privkey.pem`. Во время деплоя bypass:

- проверит срок действия сертификата и соответствие полному домену;
- проверит, что приватный ключ относится к этому сертификату;
- скопирует файлы в `/etc/vpnforge/certs`, не изменяя оригиналы.

После автоматического продления сертификата Certbot нужно повторно выполнить
деплой, чтобы bypass забрал обновлённые файлы.

## Базовые API-эндпоинты

- `GET /api/health` — статус сервера
- `POST /api/cert/validate` — валидация сертификата
- `POST /api/dns/upsert` — создание/обновление DNS A-записи
- `POST /api/secrets/load` — загрузка secrets по IP
- `POST /api/secrets/export` — экспорт secrets
- `POST /api/secrets/import` — импорт secrets
- `GET /api/clients` — список клиентов
- `POST /api/clients` — добавление клиента
- `PATCH /api/clients/{id}` — обновление клиента
- `DELETE /api/clients/{id}` — удаление клиента
- `POST /api/deploy` — запуск деплоя
- `GET /api/deploy/stream/{job_id}` — SSE-поток логов деплоя
- `GET /api/sub/{token}` — локальная подписка для клиента
- `GET /api/config/{token}/xray.json` — полный Xray-профиль с RU → direct
- `GET /api/openflux/client?ip=<ip>` — команда и ключ для OpenFlux-клиента

## OpenFlux

Проект уже содержит реальную интеграцию с upstream-репозиторием OpenFlux:

- https://github.com/p1neappleXpress/OpenFlux

Что здесь реализовано:

- модель конфигурации OpenFlux в `vpnforge/models.py`;
- генерация актуальных server/client аргументов `openflux` в `vpnforge/openflux_manager.py`;
- Ansible-задача для сборки и запуска OpenFlux на VPS в `ansible/tasks/openflux.yml`;
- UI-поля для выбора транспорта и режима в `vpnforge/web/templates/index.html`;
- данные для деплоя отправляются через backend в `POST /api/deploy`.

Поддерживаемые транспорты в проекте:

- `cupsonline`
- `yandex`
- `vyandex`
- `oneme`
- `mailru`

Режимы:

- `l4` — безопасный режим без root, TCP через userspace proxy
- `l3` — быстрый Linux-режим с raw sockets и системным RST-drop правилом

Кодеки:

- `batched` — актуальный zstd-кодек OpenFlux 0.0.3, используется по умолчанию;
- `legacy` — только для совместимости со старыми клиентами.

На VPS скачивается официальный бинарник OpenFlux 0.0.3 с проверкой SHA-256.
Архитектуры `amd64`, `arm64` и `armv7` выбираются автоматически. OpenFlux
работает отдельным systemd-сервисом и при Docker runtime для остальных протоколов.

### Важные ограничения OpenFlux в этом проекте

- клиент и сервер OpenFlux должны использовать одинаковые transport и codec;
- режим `l3` требует root/CAP_NET_RAW и автоматически ставит scoped RST-drop правило;
- cupsonline создаёт новую session при рестарте сервиса — после повторного деплоя нужно обновить клиент;
- для реального деплоя нужен живой VPS и корректная SSH-среда.

Это нормально для MVP/alpha-версии, но означает, что проект пока не является полностью универсальной production-ready реализацией всех режимов OpenFlux.

## Подключение клиентов и RU-routing

После успешного деплоя откройте строку клиента в UI:

- **Copy subscription** — копирует URL вида `https://<host>:8444/sub/<token>` для Hiddify,
  v2rayN и других клиентов с поддержкой подписок;
- **Xray JSON + RU direct** — скачивает полный Xray-конфиг, где `geoip:private`,
  `geosite:private`, `geoip:ru` и `geosite:category-ru` идут напрямую, а остальной
  трафик — через VLESS Reality;
- в секции **CLIENT ROUTING** можно отключить RU/private direct или добавить свои
  домены, которые должны открываться без VPN.

Кнопка справки в правом верхнем углу содержит инструкции по Hiddify, v2rayN и
официальным OpenFlux-клиентам. Ссылка подписки является секретом доступа — не
публикуйте её.

VLESS Reality использует TCP и `xtls-rprx-vision`, как стандартный профиль
3x-ui. После деплоя обновите подписку в клиенте: flow в старом профиле
не появится автоматически.
Если профиль был создан для XHTTP или его токен удалён, удалите его из клиента
и импортируйте свежую подписку заново. Не проверяйте новый сервер через уже
активный другой VPN: он может перехватывать соединение с VPS.

Новые установки Reality используют `www.apple.com` как сайт маскировки. При
повторном деплое старое значение `www.microsoft.com` заменяется автоматически,
при этом ключи и идентификаторы клиентов сохраняются. После такого деплоя
обновите подписку в клиенте: его SNI должен совпадать с новым значением.

Нативный деплой проверяет VLESS и Hysteria реальными запросами через прокси.
Если ответ не приходит с IP VPS, деплой завершается ошибкой, даже когда служба
активна.

Сервер подписок не занимает стандартные порты существующего nginx: с TLS он
работает на `HTTPS :8444`, без сертификата — на `HTTP :8080`. Эти TCP-порты
должны быть разрешены во внешнем firewall VPS.

Во время деплоя bypass останавливает и отключает nginx, не удаляя его
конфигурацию и сертификаты. VLESS Reality использует `TCP :443`, а Hysteria 2 —
`UDP :443`; эти два протокола могут работать на одном номере порта одновременно.

## Ограничения текущей версии

- нет полноценной авторизации/ролей;
- проект рассчитан на локальный control plane и на доверенную среду;
- сертификаты не выпускаются автоматически: их можно загрузить локально или
  выбрать уже выпущенные файлы на VPS;
- no UI/UX hardening, no multi-server orchestration;
- OpenFlux остаётся экспериментальным upstream-проектом; после обновления версии
  нужно отдельно проверить CLI, checksum релизных файлов и wire-совместимость клиента;
- для реального production deployment нужна отдельная проверка окружения и сетевой безопасности.

## Рекомендуемый сценарий использования

1. Подготовить VPS и SSH-доступ.
2. Установить зависимости через Poetry.
3. Запустить backend локально.
4. Открыть UI по адресу `http://127.0.0.1:8000/`.
5. Настроить VPS, домен, TLS, протоколы и OpenFlux параметры.
6. Нажать deploy и следить за логами.
7. После завершения проверить подписки и доступность сервисов на VPS.

## Краткий вывод

**bypass** — проект-оркестратор для VPN-стека, который уже умеет многое: деплои, кейсы с OpenFlux, управление секретами, составление подписок и работа с сервером через Ansible. Он находится в стадии зрелого MVP, но всё ещё требует аккуратной настройки окружения и проверки реального VPS-репозитория перед production-использованием.
